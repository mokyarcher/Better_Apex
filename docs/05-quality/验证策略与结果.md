# 验证策略与结果

状态：现行　更新：2026-11-02

## 证据级别

| 级别 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| Rust/前端自动化测试 | 指定逻辑、输入和状态序列符合断言 | 不证明真实游戏时序、Apex 是否接收按键或 FPS 收益 |
| 静态截图回归 | 指定图片上的页面分类/OCR路径和字段结果 | 不证明连续同局关联、总体准确率或原生分辨率表现 |
| 编译/资源检查 | 当前提交可构建，交付文件齐全 | 不证明桌面启动、窗口采集或游戏交互 |
| 桌面应用启动 | 该环境 UI/资源可启动 | 不证明目标游戏画面兼容 |
| 游戏电脑实测 | 特定设备、画面设置、游戏版本下的实际行为 | 只覆盖记录过的环境和场景，不能泛化至所有配置 |

报告结果时明确级别；不把静态样本数量写成百分比准确率，不把编译成功写成实机验收。

## 项目验证规则

- 仅运行与变更直接相关的命令；根据用户当前约定，未被要求验证时不额外运行测试或桌面程序。
- 测试使用隔离目录（如 `.local/storage-tests/`），不写入正式用户战绩，不向真实游戏或其他程序发送测试输入。
- 复用现有 `.local/rust-target-gui` 缓存；不为同一任务重复创建 Rust target 缓存。
- 样本原图不修改。不同队伍的图片不得拼成一组同局证据；派生 1080p 缩图不得标成原生 1080p 采集验证。
- 记录测试/运行的提交、命令、环境、输入集、预期和结果；失败保留错误文本和复现条件。

## 最近已知结果

截至 2026-11-01 的项目记录：45 项 Rust 回归、3 项前端测试和正式 Release 构建通过。PP-OCR 与 Windows OCR + Tesseract 对现有 14 张结算图各 14 个数字字段均通过（每引擎 196 个字段）。这些结果只对当时代码和固定样本成立。

保存后自动下一局验证只覆盖触发闸门、取消条件、单次消费和扫描码结构；**没有向真实游戏发送按键**。当前游戏电脑的按键接收、连续运行、显示模式和性能状态见[开发进度](../03-planning/开发计划与进度.md)，未实测的项目明确保持待验。

1080p样本主要是由较高分辨率缩小生成；能够检查缩放定位和 OCR 回归，不能证明原生 1080p 游戏采集的字体表现或性能。

## 常用命令

在项目根目录执行，需要时选择相关项：

```powershell
$env:CARGO_TARGET_DIR = Join-Path $PWD '.local/rust-target-gui'
cargo test --manifest-path rust-app/src-tauri/Cargo.toml --lib --offline
cd rust-app
npm.cmd test
npm.cmd run build
```

具体开发机资源准备和发布命令见[开发、构建与游戏电脑验收](../06-operations/开发构建与游戏电脑验收.md)。历史阶段的逐项测试计数、哈希和原始输出保留在 `archive/` 或 `.local/`，除非为某个具体问题复盘，不作为当前概览重复维护。
