## PP-OCR结算数字与未完成结算的新局切换（2026-11-01）

当前选择PP-OCRv6 small时，排名、小队总击杀、三人击杀／助攻／击倒／伤害及结算卡片匹配线索均由同一PP-OCR实例识别，不混用旧数字引擎。数字按现有ROI与前景完整字形界限直接送识别模型，省去数字文字检测；保留位数、格式、前导零、置信度和跨帧一致性校验。原Windows OCR＋Tesseract选项保留为明确可选路径；配置字段nickname_backend兼容旧设置文件，现在同时决定昵称与结算数字引擎。

自动复核只读取两帧数字，稳定后在最新结算证据帧读取一次三张卡片线索；数字重试不反复读取昵称卡片，没有可靠02名单时也不读取无用线索。匹配线索读取失败不会阻止已确认数字保存，失败卡片身份保留未知并写日志。最终自动昵称仍只能来自同局02单次名单，03文字不能直接提供最终昵称。

修复未保存结算时不再检查新局入口的问题：看到03后，即使尚未保存，也继续检测00／01。发现新一局加载或选传奇时，结束旧等待、清空旧名单并恢复2秒节奏，仍需新02两帧确认。不将未知数字编造成战绩，不将旧名单带入下一局；日志记录unresolved_settlement_left及最后解析结果。本次反馈原JPEG保存在image_for_test/异常识别问题2-结算后进入下一局.jpg，按原文件哈希核对，作为加载页与合成未完成状态上下文的回归；它不是上一局结算数字的证据。

## 一、对局生命周期

开启自动记录 → 00 加载（三人赛） → 01 选传奇（两个操作提示） → 只监视阶段 → 02 对局（剩余小队数量） → 连续确认 HUD → 读取左下队伍栏一次并直接采用结果 → 03 结算（小队排名和总击杀） → 每秒核对结算数据 → 昵称关联并本地保存 → 锁定当前结算页 → 检测新一轮 00 或 01 → 连续确认新一轮 02 HUD → 开始新记录。

## 02 对局阶段

连续两帧确认局内HUD后，只在确认帧读取一次左下三人昵称，各槽位直接采用这次结果，不计票、不重试。空结果或错误占用唯一一次尝试并保留未知；切出恢复不重新读取，新一局才重置。02保持常规2秒采集，只有结算确认临时改为1秒。

各HUD槽位直接采用单次清理空白后的原文，不相互补全。名单立即标记“单次识别完成”，空槽位保持待核对。

只保留一张02完整画面作为昵称来源图，不保存逐帧图。数据库来源图类型仍叫selection，兼容旧库；新记录内容是HUD图。02与03顺序可以不同，结算关联仍做一对一证据匹配。

## 03 结算阶段

样本：image_for_test 中以 03 开头的原图。使用“小队排名”和“小队总击杀”标题定位结算页，避免将匹配面板中的数字误判成结算结果。

发现第一张结算候选图后，采集间隔从常规 2 秒临时改为 1 秒。首轮用连续两帧核对，若数字仍缺失或冲突，后续每秒重新识别新帧并与上一次结果比较；一旦保存或离开结算页就回到 2 秒。

排名和小队总击杀必须稳定有效才保存。**最终自动昵称只来自同局 02 单次识别名单。**结算识别只产出数值和不可信卡片文字 `nickname_hint`，文字仅作一对一对齐线索，不加入投票，也不作为显示／存储昵称兜底。对齐成功采用名单原文，模糊对齐标记战绩归属待核对；无法对齐只保存该卡数值及未知身份，不能按位置或剩余人数补全。

匹配线索允许比较有空白分隔的开头词组，降低旗帜文字污染对匹配的影响，例如结算读为 `vjk0ok 0 DANGER` 时可与单次识别名单 `vjkook` 比较，但最终输出只能是名单里的 `vjkook`。保留整体一对一分配和歧义拒绝；完全遮挡或多个相似账号无法区分时不强配。

注释带身份来源 `voted_roster`／`manual`／`unresolved`（voted_roster保留为自动02名单的兼容标签）；保存层移除结算字段兜底，只接受有来源的名字。手动导入也不预填结算 OCR，名字只能由用户明确选名单或填写。旧待保存任务没有来源时不复用它的昵称，只保留数值；已有历史记录不据猜测批量重写。

## 二、下一局边界与防重复

当前结算页保存成功后进入锁定状态。停留、重复截图或反复识别不会产生第二条记录。

只有出现下一轮 00 加载标题或 01 选传奇提示，才开始建立下一局昵称上下文；但这不会立刻解锁。还要连续确认新的 02 HUD，才解除上一局锁定并开始新记录。这样即使结算页面停留很久，也不会把上一局当作下一局。

### 结算回退与采集中断修复

超过 20 秒没有新采集帧时，仅显示独立的暂停提示并恢复常规 2 秒间隔，不清空本局入局资格、已读证据、当前阶段或保存锁。恢复后重新收集两张有效结算帧确认，不将同一缓存帧冒充两次采样。中断后若已知对局标记一致，才继续使用保留的昵称证据；标记冲突仍拒绝混用，不可确认连续性时仅用结算画面本身的数据，昵称和本人归属保留待核对。

已经看到本局结算后，偶发 HUD 判定不会将阶段退回 02，也不会清空待确认的结算或重新解锁保存。新局仍须先有加载/选传奇证据，再确认新的 HUD；仅 OCR 对局标记变化不能解除已保存锁。前端直接使用后台阶段枚举，不再通过“局内”“名单”等提示文字推断进度。

## 三、采集节奏与性能

- 常规状态：每 2 秒最多一帧。
- 01 选传奇：仅流程检测，2秒，不解析昵称。
- 02 确认HUD后：只读取一次三人昵称，保持2秒采集，不因空读数／失败重试。
- 03 结算候选：每 1 秒一帧，直到保存、离开页面或确认失败。
- DXGI 和 OCR 在低优先级线程运行；不录制视频、不持续保存监测帧。真实游戏帧率及不同显示模式的影响只能在 Apex 所在电脑验证。

每条带 UTC／北京时间、局编号、阶段、处理帧号与采样序号。01 保留上下区域的 Windows 原文及 Tesseract 原文／置信度，另记区域融合结果；02 保留 Windows 原文和规范化结果；03 记录实际复核图的可见昵称。空字符串与调用失败区分记录，部分识别出错前已成功的输出也保留。投票事件包含各写法票数、独立帧与来源、占比、领先幅度、待核对原因、跨阶段一对一映射、最终昵称与本人归属；成功保存事件关联数据库记录 ID。未保存、采集中断、停止或下一局都不删除已写样本。

调试日志默认开启；设置开关只影响本次运行，关闭不删旧文件，重启恢复默认开启。日志 I/O 在识别后台发生，失败提示但不改变 OCR 返回值或战绩保存流程。记录的是开启后实际执行的识别调用，不能追补此前版本未保存的样本。01／02 投票中的 frame 为各采样索引，日志外层 frame 为监测处理帧号，不能把两个页面同位置当作同一玩家。日志里的昵称仍是证据，并不代表确认的身份。

### 自动保存后的界面同步

自动记录状态通过 Rust 事件通知前端；保存或待保存任务恢复后更新历史、数量和最近一场，不再依赖固定间隔查询自动状态。查看旧战绩时保留当前详情，出现“查看新记录”入口。窗口隐藏时暂缓查询历史，恢复后补读状态和历史；只有采集检查展开且窗口可见时保留 2 秒预览/采集详情查询。所有查询只读取已有画面，不提高 DXGI 取帧频率。

## 五、游戏电脑验收

1. 将更新后的 EXE 与 resources 文件夹复制到游戏电脑。
2. 开始自动记录，进入一局游戏，观察 00/01/02 状态及昵称投票结果。
3. 完成对局并停留在 03 结算页，检查是否临时变为每秒复核并只保存一次。
4. 再开一局，检查是否识别新的 00 或 01，且新 02 确认前不会复用或重开旧名单。
5. 记录状态文字、错误信息和游戏帧率体感；只有发现可复现差异时再补对应原图。
6. 保存后返回主窗口，确认最近一场、记录数量和历史列表自动更新；若正在查看旧战绩，详情应保持原记录，可通过“查看新记录”切换。

## 可选昵称 OCR（2026-11-01）
