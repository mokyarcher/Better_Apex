# Better Apex 产品计划书

版本：V0.1（立项讨论稿）  
日期：2026-10-30  
产品暂定名：Better Apex  
规划原则：一期本地战绩记录与数据汇总；成熟后扩展云端同步、分享和跨设备查看。

## 1. 项目概述

Better Apex 是一款面向 Apex Legends 玩家的个人战绩工具。用户在游戏时运行桌面客户端，工具通过屏幕画面识别和 OCR，读取结算页面中可见的本人战绩，保存至本地，提供历史查询、统计汇总和趋势分析。

**产品主张：让每一场被记录的对局，都成为可以回看的成长数据。**

一期要验证的核心假设：玩家愿意持续运行一个轻量工具，以较少操作换取可信、连续的个人战绩记录。

“实时”在一期指后台监测结算页面并及时入库，不承诺还原整场实时事件、对局录像或任意玩家的完整历史。工具只能记录运行期间实际捕获到的页面；过去的对局只能通过用户保留的截图补录。

## 2. 项目前提与市场定位

### 2.1 已核实的信息

不能把“Apex 禁止所有个人开发者使用接口”作为已确认事实。Tracker Network 提供 Apex 数据接口文档；Apex Legends Status 也提供第三方接口，其文档显示部分战绩接口存在准入限制。第三方接口的存在不代表获得官方授权，也不代表能够取得完整、持续的逐场数据。[Tracker Network 文档](https://tracker.gg/developers/docs/titles/apex)、[Apex Legends Status 文档](https://apexlegendsapi.com/documentation)。

市场已有战绩产品。Tracker 的桌面应用介绍包含历史对局和详细报告，因此本项目不能以“市场没有战绩工具”为立项依据。[Apex Legends Tracker 产品介绍](https://apex.tracker.gg/apex/app)。

本方案通过操作系统屏幕采集获取用户可见的结算画面，再在本地进行 OCR 和统计。OCR 本身只处理图像，不需要调用游戏接口或访问游戏进程。核查所阅官方资料，未发现明确禁止普通屏幕截图或本地战绩截图 OCR 的规定；EA 内容政策也允许符合条件的个人游戏内容创作，包括视频。EA 用户协议另有较宽泛的第三方程序约束，但不能仅凭该条款就认定本方案被禁止。尚未找到官方对本工具这类自动结算截图分析的明确认定；规则核查与兼容性测试作为发行准备事项，不将取得单独官方批准设为原型研发的前置条件。[EA 内容政策](https://help.ea.com/en/articles/security-and-rules/ea-content-policy/)、[EA 用户协议](https://www.ea.com/legal/user-agreement)。

以上为截至文档日期的资料核查；本计划其余功能、指标与工期均为拟定方案，不代表已经验证。

### 2.2 差异化假设

| 方向 | 用户获得的价值 | 验证方式 |
| --- | --- | --- |
| 本地优先 | 不注册也能记录，数据由自己保存 | 测试用户是否重视离线使用和备份 |
| 可核对 | 每条战绩可以查看识别依据和修改记录 | 观察用户是否愿意纠错、是否信任统计 |
| 低操作成本 | 开启记录后，正常游玩即可积累数据 | 测量需要人工处理的对局比例 |
| 清晰汇总 | 快速知道今天、最近几十场的表现 | 访谈用户是否因此调整练习计划 |

差异化仍需通过实际试用验证，不预设本产品一定比现有工具更轻量或更准确。

## 3. 目标用户与使用场景

一期建议聚焦 Windows PC 端、主要游玩大逃杀匹配或排位、愿意复盘个人表现的中文玩家。先支持经过验证的一种界面语言和少量显示配置，避免一开始覆盖所有平台与模式。

主要场景：

1. 打完一晚游戏，查看局数、胜场、场均伤害、场均击杀，以及可识别的排位分变化。
2. 查询某一天或某个英雄的对局，回看单场战绩与结算截图。
3. 比较最近 20 场与前 20 场，了解表现趋势，同时看到样本量和数据缺失情况。
4. 自动记录失败时，导入截图补录或手动修正，继续维护自己的记录。

## 4. 产品目标与一期范围

### 4.1 一期目标

形成完整闭环：**开启记录 → 捕获结算页 → 识别校验 → 本地保存 → 查询与汇总 → 纠错与备份。**

优先级定义：P0 为一期验收必须完成；P1 为 P0 稳定后的增强功能，不阻塞首版发布。

| 功能 | 优先级 | 一期要求 |
| --- | --- | --- |
| 本地玩家档案 | P0 | 创建昵称、选择当前档案；无需 EA 账号登录 |
| 截图导入识别 | P0 | 支持单张截图导入、字段预览和确认保存 |
| 自动采集 | P0 | 用户主动开启后监测指定游戏窗口的结算画面 |
| 页面识别与 OCR | P0 | 提取已验证页面中的本人核心字段 |
| 校验与去重 | P0 | 异常字段进入待确认；同一页面连续捕获不重复入库 |
| 历史战绩 | P0 | 按日期、模式、英雄（有数据时）筛选，查看与编辑详情 |
| 数据汇总 | P0 | 局数、胜率、场均击杀、场均伤害及近期趋势 |
| 本地数据管理 | P0 | 删除、CSV 导出、包含图片的备份与恢复 |
| 运行控制 | P0 | 明确显示记录中、暂停、待确认、采集异常等状态 |
| 批量截图导入 | P1 | 批量识别并处理疑似重复记录 |
| 英雄与排位专题统计 | P1 | 在相关字段质量达标后提供 |
| 自动备份提醒 | P1 | 本地提醒，不依赖服务器 |

一期不包含：账号系统、云端存储、移动端、好友查询、公开排行榜、全局玩家检索、录像分析、AI 教练、对局内战术提示。主机玩家截图导入可后续评估，不承诺首版兼容。

## 5. 核心用户流程

### 5.1 首次使用

安装客户端 → 创建本地档案 → 选择游戏窗口与显示配置 → 导入样例截图或运行检测 → 查看采集说明和截图保存设置 → 开启记录。

首次检测需要确认：能否正常截图、页面模板是否匹配、本人所在行能否定位、基础字段能否读取。不支持的配置明确提示，不静默运行。

### 5.2 自动记录

1. 用户开启记录，客户端显示状态；对普通画面进行低频页面检测。
2. 发现疑似结算页后短时间连续采样，等待画面稳定。
3. 对指定区域执行 OCR，区分本人数据、队伍数据与其他玩家数据。
4. 综合字段格式、多帧一致性和页面信息进行校验，执行对局去重。
5. 可信字段自动保存；不确定字段保留为空或进入待确认，不强行补值。
6. 入库后更新历史和统计，通过托盘或客户端给出简短反馈，不抢占游戏焦点。

如果用户过快关闭页面、画面被遮挡或采集失败，允许本场未记录。产品应解释记录条件；无法观察到的对局不伪造记录，也不宣称已知完整漏记数量。

### 5.3 查询与纠错

打开历史列表 → 筛选对局 → 查看识别字段和来源图片 → 修正或补充 → 保存 → 重新计算相关统计。

疑似重复支持人工合并或保留两条；删除与合并后统计同步更新。手动修改应保留原识别值及修改时间，以便追溯。

## 6. 数据字段与统计口径

### 6.1 字段范围

| 数据 | 获取方式与限制 |
| --- | --- |
| 本地记录 ID、档案 ID | 客户端生成，不冒充官方对局 ID |
| 采集时间 | 客户端时间，明确标注为采集时间 |
| 对局时间 | 页面确有依据时记录；否则为空，不把采集时间当精确开局或结束时间 |
| 本人击杀、伤害、小队排名 | 首批重点验证字段，以实际结算页面可见内容为准 |
| 助攻、击倒、存活时间等 | 页面可读取且识别质量达标后纳入，不假设所有模式都有 |
| 英雄、模式、地图 | 可可靠识别时保存；否则允许手选或未知，区分自动与人工来源 |
| 排位分变化 | 仅在相关页面明确可读且可关联同一场时记录，保留正负号 |
| 胜负 | 依据可信排名或明确胜利标识判断，缺少依据时为未知 |
| 证据与质量信息 | 图片引用、字段来源、原始识别值、校验结果、模板版本、修改状态 |

同一场可能跨多个结算页面，信息不得仅凭“时间接近”就盲目合并。若无法可靠关联，保留待确认状态。MVP 可先支持单一页面的核心字段。

### 6.2 统计规则

- 已记录对局数：当前筛选条件内、未删除且不是重复项的有效记录数量。
- 场均伤害：已知本人伤害之和 ÷ 本人伤害有效的对局数。
- 场均击杀：已知本人击杀之和 ÷ 本人击杀有效的对局数。
- 胜率：已确认胜场 ÷ 胜负已知的有效对局数。
- 前五率：排名前五的对局数 ÷ 排名已知的有效对局数。
- 排位分净变化：仅累加可以明确归属本场的有效分值，同时展示覆盖局数。
- 英雄统计：仅统计英雄归属明确的记录，未知英雄单列。

所有汇总展示样本量、有效字段覆盖率和统计范围。缺失值不计为 0；待确认字段不参与对应指标计算。人工修正且通过校验后可参与统计。

**一期默认不展示 K/D。**不能把每场视作一次死亡，也不能用击倒数代替死亡数；后续仅在死亡数据可靠时增加该指标。

统计只描述“本工具已记录的对局”，不包装成账号完整生涯数据。不混合不同模式的不可比指标，也不把样本相关性表达成因果结论。

### 6.3 对局中采集身份，与结算战绩关联

新增需求：结算页昵称可能被角色模型或旗帜装饰遮挡。可先从同一场对局的队伍栏或队伍介绍画面采集玩家身份，再与结算页三人的战绩对应。

处理流程：采集同场名单 → 保存昵称原文及可用身份信息 → 识别结算页战绩与可见昵称 → 进行一对一匹配 → 展示最终玩家与战绩；无法确认的关联保留待核对。

规则：

1. 本需求中的 ID 指玩家昵称，不指结算图底部的数字玩家 ID。局内昵称区域参考 image_for_test 的 01 选传奇页和 02 左下队伍栏；不能将昵称当作官方账号唯一 ID。
2. 有已验证的完整玩家 ID 时优先精确匹配；只有昵称时，先匹配完整昵称，再对残缺或 OCR 有误的昵称进行相似度比对。保留原文，避免清洗规则把不同昵称合并。
3. 只在已确认的同一场对局名单内匹配。静态图片阶段由用户明确配对；后续自动采集按本地对局会话隔离，不能仅因时间接近就沿用上一场队友。
4. 三名玩家进行整体一对一分配，避免两份战绩匹配到同一个人；队伍栏位置与结算页位置不预设相同。
5. 相似度是候选证据，不直接等于正确身份。结合可见字符、必要时的英雄信息以及第一候选与其他候选的差距判断；阈值通过配对样本验证后确定。
6. 昵称完全不可见时，单靠昵称相似度无法确认关联。存在重名、近似昵称、遮挡严重或证据冲突时，保留待核对，允许用户选择对应玩家。
7. 主界面只展示最终昵称与对应战绩，必要时提示待核对，不展示中间 OCR 文字或相似度计算过程。

当前 Rust/Tauri 版已接入本地自动记录主流程：00 加载标志 → 01 选传奇昵称采样 → 02 局内昵称复核 → 03 结算识别和存储。01 页面依据“小队静音”和“选择成为跳伞指挥官”定位，分别读取左上队伍栏与底部玩家栏，并以多帧候选投票；02 读取动态的剩余小队数作为 HUD 锚点，再从左下队伍栏补充昵称样本；03 读取小队排名、总击杀、玩家数据和可见昵称。各来源按相似度一对一关联，不假定玩家顺序一致；证据不足时保留待核对。常规采集每 2 秒最多一帧，昵称采样和结算确认临时提升到每 1 秒最多一帧。当前静态回归只使用 image_for_test 中的新 00、01、02、03 四张 2560×1440 原图，真实游戏连续对局和性能仍需在游戏电脑验收。已确认的本地记录保存到新版 SQLite，可在战绩记录中查看；新版不导入或读取旧版战绩。

关联功能的验收样本需要同一局的对局截图和结算截图，覆盖昵称完整、局部遮挡、完全遮挡、昵称近似及两张图玩家顺序不同等情况。以实际画面和用户确认建立配对，不仅凭文件名推断同场。

## 7. 页面规划

| 页面 | 主要内容 |
| --- | --- |
| 总览 | 记录开关、运行状态、待确认数量、今日及近 20 场指标、趋势 |
| 历史战绩 | 时间、模式、排名、击杀、伤害、英雄、数据状态与筛选 |
| 对局详情 | 本人数据、结算图、缺失字段、修正、删除与重复处理 |
| 数据统计 | 日期范围、模式与英雄筛选、指标趋势、样本与覆盖情况 |
| 待确认 | 低可信字段、疑似重复、未能归属的页面与处理入口 |
| 设置与数据 | 档案、采集窗口、兼容配置、图片保留、导出、备份与恢复 |

首页优先回答三个问题：是否正在记录、最近表现如何、是否存在需要处理的数据。

## 8. 技术方案与可行性验证

### 8.1 推荐架构

指定窗口画面采集 → 页面检测 → 结算画面稳定判断 → 区域裁剪与 OCR → 字段校验与去重 → 本地数据库 → 查询与统计界面。

一期采用本地 OCR、本地数据库和本地图片目录，不依赖云端识别。具体桌面框架与 OCR 引擎通过小型原型选定，不在立项阶段锁死技术栈。

数据库可优先评估 SQLite。原始数据与展示统计分开：保留字段来源、解析版本和修正记录；汇总可重新计算，后续更换 OCR 时能够对保留图片重新识别。

采集方案使用操作系统屏幕采集能力，仅分析用户可见画面，不读取游戏进程内存、不注入进程、不拦截通信、不修改游戏文件、不模拟游戏操作。采集图像可以直接在内存中交给 OCR，不必模拟按下截图键，也不必每次写入图片文件。

### 8.2 必须先解决的难点

1. **页面差异：**不同语言、分辨率、缩放比例、模式和赛季可能改变布局。建立明确的支持矩阵，每次扩大支持范围都单独验收。
2. **本人定位：**不能默认结算第一行就是本人；结合本地档案、页面布局或首次校准验证，无法确认时交由用户处理。
3. **数字与符号：**重点检查 0/8、1/7、分隔符、负号、排名和伤害数字，不能只依赖 OCR 引擎的原始置信度。
4. **重复与误合并：**同一页面停留数秒会重复采样；不同对局也可能恰好有相同数据。结合采集会话、页面进入与离开、图片相似度和字段证据判定，疑似情况保留人工判断。
5. **性能：**对局中低频检测，仅候选结算页短时提升频率；支持暂停，避免持续全屏高频 OCR。
6. **可恢复：**识别任务失败不阻塞后续采集；入库中断不产生半条记录；备份恢复可重建统计。

### 8.3 最小验证集

先确定至少一种受支持语言和两种目标显示配置，再采集具有明确标注的真实结算图片与连续页面片段。覆盖高低击杀、零伤害、大数字、胜利、提前退出、遮挡、快速切页、重复停留和相邻两场数据相同等情况。

训练或调参样本与最终验收样本分开；自动采集测试使用连续片段或实机人工标注场次，不能只测精选静态截图。

## 9. 数据、隐私与后续云端兼容

一期无需游戏账号密码，不默认上传截图、战绩或诊断日志。捕获范围尽量限定在指定游戏窗口和必要区域；截图可能包含队友昵称或聊天内容，保存策略需对用户可见。

结算证据图默认本地保存，提供关闭保存、保留期限和容量管理；关闭或清理后仍可查询结构化记录，但不再承诺能够回看来源或重新识别。

CSV 用于分析，不视作完整备份。完整备份应包含数据库、所选图片和版本清单；恢复前校验备份格式并避免直接覆盖现有档案。删除功能明确是否同时删除来源图片。

为二期预留稳定记录 ID、数据结构版本、更新时间、字段来源与删除标记，但一期不建设云服务。

## 10. 研发里程碑

以下按一名熟悉桌面开发的开发者估算，总计约 6—8 周；不包含尚无法确定的官方沟通等待、签名发行和大规模适配成本。

| 阶段 | 参考时间 | 交付与通过条件 |
| --- | --- | --- |
| 需求与样本确认 | 第 1 周 | 用户访谈、页面样本、支持矩阵、字段清单与风险结论 |
| OCR 原型 | 第 2 周 | 导入截图、正确定位本人、识别核心字段；量化准确率 |
| 本地闭环 | 第 3—4 周 | 存储、历史、详情修正、汇总、导出及备份恢复 |
| 自动采集 | 第 5—6 周 | 页面检测、稳定采样、去重、托盘状态及异常恢复 |
| 封闭测试与打磨 | 第 7—8 周 | 真实游玩验证、性能评估、修复高频问题、形成安装包 |

若 OCR 原型未达到要求，先缩小语言、分辨率或字段范围再验证。可发布截图导入测试版收集反馈，但自动记录达标前不能宣称一期自动采集目标已完成。

## 11. 一期验收指标

以下是待原型验证的目标，不是对外承诺。所有准确率都需要同时报告样本量、支持配置和拒识比例。

| 指标 | 建议目标 | 测量口径 |
| --- | --- | --- |
| 核心字段准确率 | ≥98% | 独立验收集上，击杀、伤害、排名分别计算完全正确率；漏识别计为不正确 |
| 符合条件的自动记录成功率 | ≥95% | 工具运行、配置受支持、结算页完整可见至少 3 秒的人工标注对局中，正确入库的比例 |
| 全部实测对局覆盖率 | 必须报告 | 连续测试期间所有人工标注对局中成功记录的比例，包含快速切页等失败情形 |
| 重复入库率 | ≤1% | 自动生成的有效记录中，重复记录所占比例 |
| 误合并 | 验收样本中为 0 | 专项检查不同对局被合成一条，尤其相同战绩场景 |
| 入库延迟 | P95 ≤5 秒 | 从首次完整且稳定的可识别结算画面到记录可查询 |
| 人工处理比例 | ≤10% | 全部已捕获对局中，需要修正或确认才能得到核心数据的比例 |
| 稳定性 | 连续运行 3 小时 | 无崩溃；采集失败可恢复，已入库数据不丢失 |
| 数据一致性 | 验收用例全部通过 | 编辑、删除、合并、备份恢复后，明细与汇总一致 |

性能验收先建立基准机器及固定场景，比较开关工具时的平均帧率、1% low、CPU 与内存。暂定平均帧率下降控制在 2% 内，同时检查是否出现可感知卡顿；达不到时降低采样成本或收缩支持配置。

同时报告“自动直接成功率”和“人工修正后可用率”，防止用大量人工补录掩盖自动化不足。

## 12. 内测与产品价值验证

首批招募 10—20 名目标玩家，持续试用两周。通过用户主动提供的反馈或自愿导出的匿名统计，观察：

- 首次安装到成功保存首场战绩是否顺畅。
- 用户是否愿意在后续游玩时继续开启记录。
- 用户每次游戏结束后是否主动查看汇总。
- 错误主要来自页面未捕获、本人定位、OCR 还是重复判断。
- 用户实际最需要哪些指标，是否愿意为以后云端同步付费。

一期北极星指标建议为：**每周有至少一次查阅行为的有效记录用户数**。本地版不默认采集该指标；内测通过自愿反馈估算，云端上线后再设计经同意的统计机制。

继续投入的建议门槛：技术验收通过，且两周结束时至少一半内测用户愿意继续使用。该比例仅用于小样本决策参考，不能当作市场规模结论。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 界面更新 | 识别失效或字段错位 | 模板版本管理、更新回归、无法匹配时暂停自动写入 |
| 漏记与误识别 | 用户不信任统计 | 明示覆盖范围、来源可查、待确认与补录、分类统计失败原因 |
| 屏幕采集与游戏兼容 | 黑屏、捕获失败或运行冲突 | 使用系统采集能力，实测全屏及无边框等支持配置；保留用户导入截图的模式。当前没有证据表明普通结算截图 OCR 本身被禁止 |
| 兼容范围膨胀 | 工期失控 | 首版限定平台、语言、模式和显示配置 |
| 数据损坏或迁移失败 | 战绩丢失 | 事务写入、迁移前备份、完整恢复演练 |
| 本地截图占用空间 | 长期使用成本增加 | 设置容量和保留期限，允许仅保留结构化数据 |
| 相较现有工具价值不足 | 用户不留存 | 用真实玩家试用检验本地、可纠错、低干扰的价值 |

## 14. 二期及后续演进

### 二期：个人云端战绩库

新增账号与设备绑定、可恢复的增量同步、网页或手机浏览器查看、选定范围的分享链接。先实现个人数据跨设备，再考虑社交。

关键规则：上传必须由用户主动开启；默认仅上传必要的结构化数据，截图另行选择；历史本地数据是否上传单独设置。同步具备稳定 ID、重试去重、冲突处理与删除传播，离线仍可正常记录。

分享默认私密，由用户选择具体对局或报告，链接可撤销；公开前处理其他玩家标识。OCR 记录与人工修正均可能失真，不能宣传为官方认证数据，也不宜直接用于竞技排行榜或赛事判定。

二期启动条件：本地自动记录与备份稳定、模板维护可持续、试用用户有明确跨设备需求，并完成云端数据与规则评估。

### 后续：围绕数据积累扩展

可评估长期趋势、周报、训练目标、队伍共享和更多截图来源。录像分析、AI 建议与社交体系另行立项，避免拖慢战绩记录主链路。

## 15. 商业模式与投入原则

一期以验证需求为主，暂不强制订阅。优先保障本地记录、纠错与数据导出的体验。

后续可以评估云存储、多设备同步、长期报告等付费服务；定价依据实际存储、带宽、维护成本及用户付费意愿制定。暂不估算收入，不预设广告或出售玩家数据作为商业前提。

一期主要投入包括桌面开发、OCR 调试、真实样本整理、兼容性测试及发行维护；即使不建服务器，也需考虑安装包分发与后续更新成本。

## 16. 近期行动清单

1. 收集本人和获同意测试玩家的真实结算截图，确认现有页面能稳定提供哪些字段。
2. 确定首版支持的 Windows 环境、语言、模式、分辨率和显示模式。
3. 访谈 5—10 名玩家，对比其当前记录方式与已有工具的使用体验。
4. 制作“导入截图 → 识别本人击杀/伤害/排名 → 保存 → 查看汇总”的最小原型。
5. 用独立样本验收 OCR，再扩展后台自动采集与连续游玩测试。

**立项建议：先把“可靠地记录一场，并能解释记录从何而来”做扎实，再扩展自动化覆盖率与云端服务。**
