# Rust 阶段 C1：结算字段结构化识别

## PP-OCR结算数字与未完成结算的新局切换（2026-11-01）

当前选择PP-OCRv6 small时，排名、小队总击杀、三人击杀／助攻／击倒／伤害及结算卡片匹配线索均由同一PP-OCR实例识别，不混用旧数字引擎。数字按现有ROI与前景完整字形界限直接送识别模型，省去数字文字检测；保留位数、格式、前导零、置信度和跨帧一致性校验。原Windows OCR＋Tesseract选项保留为明确可选路径；配置字段nickname_backend兼容旧设置文件，现在同时决定昵称与结算数字引擎。

自动复核只读取两帧数字，稳定后在最新结算证据帧读取一次三张卡片线索；数字重试不反复读取昵称卡片，没有可靠02名单时也不读取无用线索。匹配线索读取失败不会阻止已确认数字保存，失败卡片身份保留未知并写日志。最终自动昵称仍只能来自同局02单次名单，03文字不能直接提供最终昵称。

修复未保存结算时不再检查新局入口的问题：看到03后，即使尚未保存，也继续检测00／01。发现新一局加载或选传奇时，结束旧等待、清空旧名单并恢复2秒节奏，仍需新02两帧确认。不将未知数字编造成战绩，不将旧名单带入下一局；日志记录unresolved_settlement_left及最后解析结果。本次反馈原JPEG保存在image_for_test/异常识别问题2-结算后进入下一局.jpg，按原文件哈希核对，作为加载页与合成未完成状态上下文的回归；它不是上一局结算数字的证据。

验证：40项Rust、3项前端测试通过。14张结算图×14字段，PP及原引擎各196字段全部符合人工真值；另有74／665／117反馈图与下一局加载回归。Debug双引擎完整单图均值约PP1591ms／原引擎520ms，包含不同昵称通路，不能据此宣称数字单项耗时或实战精度／FPS提升；单张反馈图的数字独立328ms、一次卡片线索1151ms仅为开发机样本。报告在.local/ppocr-settlement-review/comparison.json与feedback.json，测试不写正式战绩。

## 传奇选择界面的昵称候选

新增手动识别类型“选传奇界面”。裁剪框收紧到昵称文字。每个队伍位置最多产生四个候选：左上和底部玩家栏分别送入 Windows OCR、Tesseract。中文候选比较时移除空白，其他候选折叠连续空白并忽略大小写；按完全相同的规范化文本计票，票数最多者作为建议昵称，平票时优先 Windows OCR。算法不计算字符级相似度，也不使用识别置信度；因此建议昵称仍可能只是单路候选，不能等同于已确认。

使用新 01 选传奇原图读取左上队伍栏与底部玩家栏；当前手动页面展示两个区域的识别候选。实际自动记录会在该页面最多采集 3 帧，并对两个区域和时间样本投票。新 01 的前三个昵称中，前两位可形成较稳定候选，第三位在单张截图上仍可能出现明显差异，因此不稳定结果保持待核对。

自动流程已把选传奇昵称采集接入状态机，并在 02 局内 HUD 读取左下队伍栏复核。01／02 投票是唯一自动昵称来源；03 卡片粗文字只用于一对一对齐线索，不能作为名字展示、保存或兜底。相似度不足时只保存数值及待核对身份，不假定不同页面玩家顺序一致。自动流程、采集间隔和实机测试方式见[阶段 D 自动监测说明](Rust阶段D自动监测.md)。新版存储见[阶段 C2 说明](Rust阶段C2新版数据库初始化.md)。
